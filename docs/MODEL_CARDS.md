# Model Cards

## 1. Rule + rolling z-score health/RUL model (`simulator.js`)

**Status:** implemented, running today.

- **Purpose:** per-tick composite health score (0–100), remaining-useful-life
  estimate (engine hours), and predicted-fault classification with a
  confidence percentage.
- **Type:** not a trained ML model — a hand-tuned rule engine. There is no
  training data, no fit step, and no held-out evaluation set; all constants
  (penalty weights, z-score thresholds, RUL decay rate) are hard-coded in
  `computeHealthAndPrediction()`.
- **Inputs:** the 9 current sensor readings, their nominal/warning/critical
  classification (`classify()`), and a rolling z-score per sensor computed
  over the last 30 samples (`HISTORY_WINDOW`, ~60s of history at the 2s tick).
- **Outputs:** `health` (100 minus accumulated penalty, clamped 0–100),
  `predictedFault` (the `FAULT_TYPES` entry whose affected sensors show the
  strongest combined warning/critical + z-score signal, if score ≥ 1.6), and
  `rul` (exponentially relaxes toward `200 + health*3.2`, clamped 0–900
  hours).
- **Known limitations:**
  - Thresholds and penalty weights are illustrative, tuned by hand for a
    convincing live demo, not fit against real engine failure data.
  - The z-score is computed against the engine's own recent history, so a
    fault that develops slowly relative to the 30-sample window will be
    under-detected (the rolling mean drifts with it).
  - RUL is a smoothed function of the current health score, not a
    time-to-failure model conditioned on fault type or severity trajectory —
    two engines with the same instantaneous health but very different
    fault dynamics get the same RUL trend.
  - **Not validated against any real engine telemetry.** This is a purely
    synthetic-data model; there is no Rotax-912 (or any other engine)
    ground-truth dataset behind it.

## 2. `analytics/` — rate-aware health index, multivariate anomaly detector, RUL estimator, explainability

**Status:** described here prescriptively per the master plan; verify
against the actual code in `analytics/` once merged, as implementation
details may differ from this card.

- **Purpose:** go beyond `simulator.js`'s per-sensor threshold + own-history
  z-score by (a) making the health index rate-of-change aware (penalize a
  sensor trending sharply toward a threshold, not just one that has already
  crossed it), and (b) catching jointly-anomalous-but-individually-normal
  sensor combinations that per-sensor thresholds structurally cannot see
  (e.g. CHT/EGT/fuel-flow jointly drifting in a pattern no single threshold
  flags).
- **Type:** rate-aware health index — still rule-based (thresholds on
  slope, not just level). Multivariate anomaly detector — intended as an
  Isolation Forest or lightweight autoencoder per the master plan, trained
  on simulated "healthy" flight data (no injected fault active) so it
  learns the joint distribution of nominal operation and flags deviations
  from it. RUL estimator — intended as gradient-boosted regression over
  engineered rolling features (mean/std/slope per sensor), trained on
  labeled simulated missions with scheduled fault-injection severity and
  known time-to-failure.
- **Training data:** entirely synthetic, generated by running many
  simulated missions (via `engine_sim/` mission profiles once available)
  with scheduled fault injection at varying severity/onset — there is no
  real engine dataset anywhere in this project.
- **Known limitations:**
  - Any model trained here has only ever seen this project's own simulator
    output. It cannot be assumed to generalize to a real engine's noise
    characteristics, sensor cross-correlations, or failure signatures.
  - The fault taxonomy it's trained against is limited to the categories
    actually implemented in the simulator (see `docs/FAULT_TAXONOMY.md`) —
    it cannot detect fault modes (misfire, coking, sensor drift/failure)
    that were never injected into its training data.
  - Explainability output (e.g. SHAP values or feature-importance) explains
    what the model attended to, not what is physically true of a real
    engine — it should be read as "why the model flagged this," not as an
    engineering diagnosis.
  - **Not validated against any real engine telemetry.**

## 3. `ai/` — RAG + Gemini "AI Engine Situation" narrative

**Status:** implemented, running today (`ai/knowledgeBase.js`,
`ai/retriever.js`, `ai/geminiClient.js`, `ai/analysisEngine.js`).

- **Purpose:** turn the current numeric snapshot for one engine into a
  short plain-language situation report for a flight-ops officer (e.g.
  "oil pressure has dropped to 38 psi against a 45 psi warning threshold
  ... recommend reducing power").
- **Type:** retrieval-augmented generation over a small, hand-written,
  hand-tagged knowledge base (`knowledgeBase.js`) — tag-overlap retrieval
  (`retriever.js`, not embeddings/vector search) against the engine's
  active/predicted fault and any out-of-nominal sensors, then a single
  Gemini `generateContent` call (`geminiClient.js`) grounded on the
  retrieved docs plus the live telemetry JSON.
- **Inputs:** one engine's full snapshot (readings, statuses, health, RUL,
  active/predicted fault, recent alerts, altitude/airspeed/hours) plus
  fleet-level context (mission reliability, critical-engine count).
- **Outputs:** a ≤120-word narrative, cached per engine, re-generated when
  the engine's severity/fault state changes or after
  `AI_ANALYSIS_INTERVAL_MS` (default 5 min) elapses, throttled globally by
  `GEMINI_MIN_GAP_MS` (default 13s) to avoid bursting free-tier Gemini rate
  limits.
- **Known limitations:**
  - The narrative is only as correct as the underlying rule-based health/
    fault model (model 1 above) that feeds it — Gemini is grounding
    language on numbers the simulator produced, not independently
    reasoning about engine physics.
  - Retrieval is tag-based over a small hand-curated corpus; it will not
    surface relevant knowledge outside that corpus's coverage, and
    silently degrades to "nothing relevant retrieved" rather than erroring.
  - **Fails soft by design:** if `GEMINI_API_KEY` is unset or a call
    errors/times out/rate-limits, a one-line rule-based fallback sentence
    is shown instead, clearly distinguishable in the response (`error`
    field set, `model: null`) but visually similar in the dashboard —
    operators should not assume every situation-report line came from the
    LLM.
  - Not a safety-of-flight system: this is a demo/explanatory layer, not a
    certified advisory source, and it depends on an external third-party
    API (Gemini) being reachable and within quota.
